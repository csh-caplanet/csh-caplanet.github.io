매뉴얼 챗봇 — PHP 하나에서 도커 서비스까지, 단계별 구성과 성능

제품을 고르고 질문하면 우리 매뉴얼 · 영상 자막 · 예상 질문을 근거로 답하는 챗봇(공개된 제품 상담 챗봇 화면을 참고한 예시)을, 가장 단순한 PHP 판에서 시작해 이미지까지 다루는 도커 서비스로 키우는 순서. 두 AI(Claude · Codex)에게 따로 물어 비교했다.

2026-11-05 · 학습 노트 · 앞 글: 구성안 비교

1. 본보기 — 공개된 제품 상담 챗봇 화면
  • 화면: 첫 화면에서 제품 고르기 → 채팅, 위에 언어 설정. 어떤 LLM 을 쓰는지 화면 아래에 밝힌다.
  • 앞단: React 한 장짜리 앱(SPA), 문구는 언어별 translation.json.
  • 뒷단: 답을 글자 단위로 흘려 보내는 스트리밍 방식이다. 이런 화면은 LangChain 의 이벤트 스트리밍(astream_events)으로도, 직접 짠 SSE 로도 만들 수 있다.
  • 교훈: 사용자가 「빠르다」 고 느끼는 건 전체 시간보다 첫 글자가 뜨는 시간이다 — 스트리밍이 사실상 필수.
2. 1단계 — PHP 하나로 가장 단순하게
브라우저 질문 칸 → PHP 컨트롤러 → [매뉴얼 글 + 자막 + 예상 질문 전부를 system 프롬프트에, 캐시] → LLM API → 글자 흘려 보내기(SSE) → 화면
  • 새로 만드는 것: 서비스 클래스 1개 · 주소 1개 · 채팅 화면 1장. 검색 · 벡터 DB · 새 컨테이너 없음.
  • 자료: 노션 Markdown 내보내기 + 그림 속 조작법을 글로 + 예상 질문 표. 쪽마다 「제품 · 메뉴 · 언어 · 원본 링크 · 그림 주소」 머리말을 붙여 둔다(2 · 3단계에서 그대로 씀).
  • 이미지: 답 끝에 근거 쪽의 그림 주소를 그대로 붙여 보여 준다(모델이 그림을 보는 건 아님).
  • 다국어: 자료는 한국어 하나, 「질문한 언어로 답하라」 지시. 제품 고르기 · 언어 설정은 화면에서.
  • 한계: 자료가 프롬프트에 다 들어갈 때까지만. 스트리밍 동안 PHP-FPM 일꾼 하나를 계속 붙잡는다.
3. 2단계 — PHP + 검색으로 필요한 쪽만
질문 → 이미 쓰는 검색 엔진(Meilisearch 등, 제품 · 언어로 거르기) 상위 5~8쪽 → 그 쪽만 프롬프트에 → LLM → SSE → 답 + 근거 링크 + 그림
  • 자료가 커져도(매뉴얼 전 버전 · 모든 자막) 프롬프트가 작아져 질문당 비용 · 첫 글자 시간이 준다.
  • 매뉴얼 그림은 미리 한 번 비전 모델로 「이 그림은 무엇을 하는 화면인지」 설명을 뽑아 검색 색인에 넣는다 → 그림 내용으로도 찾힌다.
  • 사용자 스크린샷 질문: 이미지를 LLM API 에 같이 보내면 PHP 로도 된다(비전 지원 모델). 다만 업로드 크기 · 시간이 FPM 을 더 붙잡는다.
  • 예상 질문 표는 정답지로 쓴다 — 자동 채점으로 「찾기 실패 / 답 틀림」 을 갈라 본다.
  • 질문 · 답 · 찾은 쪽을 로그로 남겨, 못 찾은 질문을 매주 자료에 보탠다.
4. 3단계 — 도커 서비스로, 빠르고 이미지까지
브라우저 ⇄ 웹앱(로그인 · 권한 · 로그만, 토큰 발급) ⇄ 챗봇 서비스 컨테이너(Python FastAPI 비동기 또는 Node) ⇄ 벡터 DB 컨테이너(Qdrant 등) + LLM API
+ 적재 일꾼 컨테이너(노션 · 자막 · 그림을 잘라 임베딩)
  • 섞어 찾기: 낱말 검색(BM25) + 의미 검색(다국어 임베딩) + 재정렬 → 「다른 말로 물어도」 찾는다. 다국어 임베딩을 쓰면 외국어 질문을 한국어 자료에 맞출 수 있다 — 언어별 품질은 실측이 필요하다.
  • 이미지: 그림마다 ① 비전 모델 설명 글 ② 이미지 임베딩을 같이 저장. 사용자 스크린샷 → 이미지 임베딩으로 「어느 메뉴 화면인지」 먼저 찾고, 그 쪽 글 + 그림으로 답.
  • 속도: 비동기 서버라 스트리밍 수백 개를 일꾼 몇 개로 버틴다. 같은 질문은 Redis 답 캐시.
  • LangChain 은 선택이다. LangChain 이벤트 스트리밍을 쓰면 빨리 붙고, 직접 짜면 덜 무겁다.
  • 운영: 컨테이너 2~3개 · 벡터 DB 백업 · 배포 매니페스트가 늘어난다.

8. PHP-FPM 스트리밍의 병목
  • FPM 은 요청 하나가 끝날 때까지 일꾼 하나를 잡는다. LLM 답은 수 초~수십 초라, 일반 화면 요청과 일꾼 풀을 나눠 먹는다.
  • 대처: 챗봇 전용 FPM 풀(다른 소켓) · nginx 에서 FPM 직결 경로는 fastcgi_buffering off(또는 응답 헤더 X-Accel-Buffering: no) · 질문당 시간 제한 · 사용자별 횟수 제한.
  • 그래도 모자라면 그 지점이 3단계(비동기 서비스)로 옮길 신호다.
9. Codex 의견

같은 물음을 Claude 결론 없이 Codex 에 따로 물었다. 수치는 Codex 도 「측정 필요」 로 남겼다.

Claude 와 다른 점

  • 1단계: 자료를 통째로 넣지 않고 DB 에서 질문에 맞는 자료를 찾아 넣는다. 처음엔 스트리밍 없이 완성된 답을 한 번에 돌려준다. 스크린샷 질문은 범위 밖.
  • 2단계: 기존 Meilisearch 로 찾고 SSE 로 흘려 보낸다. 다른 표현을 놓치면 Meilisearch 하이브리드(의미) 검색을 더하면 되고, 별도 벡터 DB 는 아직 필요 없다고 봤다.
  • 3단계: 스크린샷은 크기 · 형식 검사 뒤 질문 + 찾은 매뉴얼 그림과 함께 비전 모델에 보낸다. 별도 서비스는 FPM 점유를 줄이지만 모델 응답 자체가 빨라진다는 보장은 없다.
  • 재는 법: 첫 글자 · 완료 시간의 p50/p95, 동시 접속별 실패율, 실제 API 사용량 · 요금, 출처가 맞는 답의 비율.
  • FPM 병목: Nginx FastCGI 버퍼링이 켜져 있으면 글자가 모여서 뜬다 → 채팅 경로만 끄고, FPM 대기열 · max children reached 를 재다가 포화되면 3단계로.
  • 화면: 제품 선택 · 언어 설정 · 채팅은 1단계부터, 글자 흐름은 2단계, 스크린샷 업로드는 3단계.

참고 문서: Meilisearch 하이브리드 검색 · Claude 스트리밍 · Claude 이미지 입력 · Nginx FastCGI 버퍼링

10. 결론
  1. 1단계로 데모 — 메뉴 하나 · 예상 질문 50개 · 제품 고르기 + 언어 설정 화면은 1단계에서도 된다.
  2. 시험지로 재고, 자료가 커지거나 정답률이 막히면 2단계.
  3. 스크린샷 질문 · 동시 사용자가 필요해지면 3단계 도커 서비스 — 이때 LangChain 은 써도 되고 안 써도 된다.
  4. 어느 단계든 자료 머리말(제품 · 메뉴 · 언어 · 링크 · 그림)과 시험지는 그대로 넘어간다.

둘이 같은 결론: 1단계로 답 품질부터 보고 → 찾기가 어려워지면 2단계 → 스크린샷 · 동시 접속이 필요하면 3단계. 근거 없으면 「모른다」, 답마다 출처.
갈리는 곳: 1단계에서 자료를 통째로 넣을지(Claude) DB 에서 찾아 넣을지(Codex), 2단계 의미 검색을 Meilisearch 하이브리드로 할지(Codex) 3단계 벡터 DB 로 미룰지(Claude).

R1. 한눈에 — 무엇을 알았나
  1. 속도는 충분하다. 1 · 2단계 모두 첫 글자가 1초 남짓, 답 완료가 2~3초다. 단계보다 모델과 답 길이가 시간을 정한다.
  2. 답 품질은 Sonnet 이 낫다. 한국어 질문 50개 중 자동 통과가 Sonnet 40 · 36, Haiku 27 · 29 (1단계 · 2단계).
  3. 2단계 키워드 검색은 외국어 질문에서 무너진다. 한국어 질문은 정답 쪽을 48/50 찾았지만 영어 · 일본어 · 중국어 · 베트남어 · 크메르어는 10개 중 0~1개. 1단계(통째로 넣기)는 이 문제가 없다.
  4. PHP-FPM 은 스트림 하나가 일꾼 하나를 잡는다. 동시 사용자 N 명을 밀리지 않게 받으려면 일꾼이 약 N 개 필요하고, 모자라면 일반 페이지 요청까지 같이 막힌다.
  5. 자료의 그림 주소가 토큰의 약 2/3. 주소를 빼면 프롬프트가 26,125 → 8,834 토큰으로 줄었다. 그림은 화면에서 근거 쪽에 붙이면 된다.

R6. PHP-FPM 동시 사용자 — 가짜 LLM 으로

R7. 이 숫자로 정한 것 · 아직 모르는 것
  1. 데모는 1단계 + Sonnet — 자료가 작아 통째로 넣어도 1초대에 첫 글자가 나오고, 외국어 질문에도 자료를 다 보고 답한다.
  2. 자료의 그림 주소는 빼고, 화면에서 근거 쪽 그림을 붙인다.
  3. 2단계로 갈 때는 다국어 검색부터 손본다 — 지금 그대로면 외국어 질문은 근거를 못 받는다.
  4. 스트리밍을 PHP-FPM 에 둘 거면 채팅 전용 풀을 따로 두고, 동시 사용자 수만큼 일꾼을 잡는다.
