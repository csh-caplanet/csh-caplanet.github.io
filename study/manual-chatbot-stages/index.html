매뉴얼 챗봇 두 가지 — 어떻게 만들고 어떻게 시험했나

CAD 프로그램과 재단 배치 프로그램의 공개 매뉴얼 427쪽을 근거로 답하는 챗봇을, 같은 화면 · 같은 Claude 모델로 PHP 판과 도커 판 두 가지로 만들었다. 그리고 난이도 10단계 × 6개 언어 질문으로 둘을 나란히 시험했다.

2026-11-05 · 학습 노트 · 앞 글: 구성안 비교

  1. 매뉴얼을 글 조각으로 잘라 두고, 질문이 오면 관련 조각 5개를 찾아 Claude 에게 건네 답하게 했다. 두 판은 「찾는 방법」만 다르다.
  2. 도커 판이 더 잘 찾고 더 잘 맞혔다 — 정답 쪽 찾기 45/60 (PHP 판 32/60), 정답 36/66 (PHP 판 20/66).
  3. 첫 글자가 뜨는 시간도 도커 판이 빨랐다 — 중앙값 1.6초 (PHP 판 2.7초).
  4. 자료에 없는 질문 6개는 두 판 모두 6/6 「매뉴얼에 없다 · 고객센터 안내」로 답했다. 반면 증상으로 묻기(6단계) · 여러 쪽 잇기(9단계) · 최근 업데이트(10단계)는 두 판 모두 정답이 0~1개였다.
  5. 틀린 이유는 대부분 Claude 가 아니라 자료 자르기 · 검색어 처리였다. 원인 5개를 고쳐 다시 재는 중이다.

정답 수에는 자료 밖 질문을 바르게 거절한 6개가 두 판 모두 들어 있다. 채점은 Claude Sonnet 이 자동으로 했고, 사람이 8건을 직접 읽어 8건 모두 같은 판정이었다.

앞의 두 칸(자르기)은 자료가 바뀔 때 한 번만 한다. 뒤의 네 칸이 질문마다 돈다. 자세한 것은 「어떻게 만들었나」 탭에.

먼저 낱말 10개 한 줄씩
RAG
질문과 관련된 자료를 먼저 찾아 AI 에게 같이 건네고, 그 자료로만 답하게 하는 방식.
청크
매뉴얼을 제목 기준으로 500~800자씩 자른 글 조각. 검색은 쪽이 아니라 조각 단위로 한다.
임베딩
글을 「뜻」을 담은 숫자 목록(벡터)으로 바꾸는 것. 뜻이 비슷하면 숫자도 가깝다.
하이브리드 검색
뜻으로 찾기(임베딩)와 낱말로 찾기(키워드)를 같이 돌려 결과를 섞는 검색.
RRF
두 검색 결과의 「순위」만 보고 점수를 매겨 하나로 합치는 간단한 섞기 공식.
SSE
서버가 답을 다 만들기 전에 글자를 조금씩 흘려 보내는 방식. 채팅 글자가 타자 치듯 뜬다.
프롬프트 캐시
매번 똑같이 보내는 앞부분(지시문)을 Claude 쪽에 잠시 저장해 두고 싸고 빠르게 다시 읽는 기능.
검색 적중
미리 정해 둔 정답 쪽이 찾은 상위 5조각 안에 들어 있었나.
첫 글자 시간
질문을 보낸 뒤 화면에 첫 글자가 뜨기까지. 사용자가 느끼는 「빠르다」는 대부분 이것이다.
부분 정답
요점 일부만 맞힌 답. 이 글의 「정답」 숫자에는 넣지 않았다.
매뉴얼 모으기 17곳 · 427쪽

공개된 매뉴얼 주소 17곳(공개 문서 사이트 두 곳 + 안내 영상 1개)의 첫 쪽과 하위 쪽을 전부 모았다. 브라우저 자동화(Playwright)로 쪽을 열고, 접힌 칸은 모두 펼쳐서 읽었다.

합계427
  • 글자 195,243자 · 그림 1,512장 · 약 97,600 토큰(글자 수 ÷ 2 로 어림).
  • 쪽마다 머리말에 제품 · 언어 · 상위 메뉴 · 원본 주소 · 그림 목록을 붙여 저장했다. 답에 출처와 그림을 붙일 때 이 머리말을 쓴다.
  • 제목 기준으로 잘라 글 조각 712개. 도커 판은 조각 앞에 「제품 > 메뉴 > 쪽 제목」을 붙여 어디 글인지도 검색에 걸리게 했다. 그림만 있고 글이 30자도 안 되는 조각 60개는 검색 순위에서 뒤로 밀었다.
  • 한계: 그림 속 글자는 읽지 않았다. 글이 거의 없는 쪽이 42개다.
화면 두 판이 같은 화면을 쓴다

실제 화면을 단순하게 다시 그린 그림이다. 사진 단추는 도커 판에서만 동작한다.

  • 위에서 제품 · 언어를 고르고 묻는다. 답은 글자가 흘러나오듯 뜬다(SSE).
  • 답 아래에 Claude 가 인용한 쪽이 번호 칩으로, 그 쪽의 그림이 작은 그림으로 붙는다.
  • 지시문은 두 판이 같다 — 「찾은 근거 안에서만 답하고, 없으면 모른다고 하고 고객센터를 안내하라 · 질문한 언어로 답하라」.
PHP 판 — 이미 있는 PHP 서버에 붙이는 길
  • 브라우저
  • 내 서버 안 (PHP-FPM · 검색 엔진)
  • 바깥 Claude API
  • PHP 8.3 + PHP-FPM + nginx, 검색은 키워드 검색 엔진(Meilisearch).
  • 키워드 검색은 낱말이 같아야 찾는다. 자료가 한국어라, 질문에 한글이 없으면 Claude Haiku 가 매뉴얼 쪽 제목 목록을 보고 한국어 검색어로 바꾼 뒤 찾는다.
  • 답은 Claude Sonnet 이 쓰고 PHP 가 글자를 그대로 흘려 보낸다. 그동안 PHP-FPM 일꾼 하나가 묶인다.
  • 색인은 712조각에 2.6초.
도커 판 — 뜻으로도 찾는 별도 서비스
  • 브라우저
  • 내 서버 안 (파이썬 서비스 · 벡터 DB · 로컬 임베딩)
  • 바깥 Claude API
  • 컨테이너 3개 — 파이썬 서비스(FastAPI, 비동기), 벡터 DB(Qdrant), 로컬 임베딩(multilingual-e5-large, CPU 에서 돈다).
  • 질문을 임베딩해 뜻이 가까운 조각 20개, 키워드(한글 두 글자씩 끊기)로 낱말이 맞는 조각 20개를 찾고 RRF 로 섞어 5개를 고른다.
  • 다국어 임베딩이라 대부분 언어는 번역 없이 찾는다. 임베딩이 약한 크메르어만 Haiku 가 한국어 검색어를 더 만든다.
  • 사진을 같이 보내면 Claude 가 사진과 근거를 함께 본다. 같은 질문은 답을 기억해 두었다가 바로 돌려준다(시험 때는 껐다).
  • 색인은 712조각에 302초(CPU 임베딩, 조각당 약 0.42초). 임베딩 모델을 처음 받을 때 2.2GB.

시간은 질문마다 잰 값의 중앙값. 답 모델은 두 판 모두 Claude Sonnet 5.5(생각 끔 · 짧게), 같은 지시문.

검색 방식은 이렇게 골랐다 처음 13쪽 자료로 잰 값

도커 판을 만들 때 같은 50문항을 6개 언어로 옮겨, 상위 5조각 안에 정답 쪽이 들었는지만 쟀다(Claude 호출 없음).

  • 그래서 기본은 「섞기」, 크메르어만 Haiku 검색어를 더했다(같은 크메르어 10문항에서 6/10 → 10/10). 다시 순위 매기기는 CPU 에서 질문당 2.6초라 껐다.
  • 13쪽짜리 작은 자료라 찾기가 쉬운 편이었다. 427쪽으로 늘린 실제 시험 결과는 「시험 결과」 탭에.
시험지는 이렇게 만들었다 10단계 × 6언어 + 자료 밖 = 66문항

질문 10개를 쉬운 것부터 어려운 것까지 한 단계씩 만들고, 각각 6개 언어(한국어 · 영어 · 일본어 · 중국어 간체 · 베트남어 · 크메르어)로 옮겼다. 여기에 매뉴얼에 없는 질문 1개 × 6개 언어를 더했다. 질문마다 정답 쪽과 답에 들어가야 할 요점을 미리 적어 두었다.

제품 이름은 이 글에서 일반 이름으로 바꿨다. 단계는 질문 내용으로 정한 것이라, 숫자가 클수록 꼭 어렵다는 뜻은 아니다.

재고 채점한 방법

  • 화면과 똑같은 경로로 질문을 보내고(동시 3개), 첫 글자 · 끝까지 걸린 시간을 보내는 쪽(클라이언트)에서 쟀다. 같은 답 재사용은 껐다.
  • 검색 적중 = 미리 정한 정답 쪽(한국어 · 영어 짝 중 하나)이 상위 5조각 안에 있었나.
  • 채점은 Claude Sonnet 이 「요점」과 답을 비교해 정답 · 부분 정답 · 오답 · 바른 거절로 나눴다. 사람이 8건을 읽어 대조했고 8건 모두 같았다.
  • Claude 호출: 답 191회(Sonnet 132 · Haiku 59) + 채점 132회.

틀린 이유 5가지
  1. 자를 때 단축키 제목이 사라졌다 (두 판). 매뉴얼은 「(VV) 직각선을 그릴 때 쓰는 도구」처럼 제목에 단축키를 적고 바로 다음 제목으로 넘어가는데, 본문 없는 제목 줄이 조각에서 빠졌다. 정답 쪽은 찾고도 「단축키를 못 찾았다」고 답했다(1단계 정답 PHP 1 · 도커 3). 매뉴얼 대부분이 이 모양이라 영향이 크다.
  2. PHP 판이 일본어를 한국어로 착각했다. 「한글이 있나」 검사 규칙이 일본어 쉼표 · 마침표(、。)에도 걸려 번역을 건너뛰었고, 일본어 그대로 키워드 검색을 했다(일본어 적중 2/10).
  3. PHP 판은 한국어 문장을 통째로 검색했다. 「자동 배치 · 재배치」 같은 핵심어보다 다른 낱말이 앞섰다(한국어 적중 4/10). 한국어도 검색어를 다듬어야 한다.
  4. 증상으로 묻는 질문은 쪽 제목과 안 맞는다 (두 판). 「길이 넣는 창이 안 떠요」의 답은 「대화창 켜기(F9)」 쪽인데, 선 그리기 쪽만 찾아 F9 를 말하지 못했다(6단계 도커 0/6).
  5. 업데이트 기록 한 쪽이 너무 크다 (두 판). 40여 조각으로 쪼개져 아무 질문에나 걸리고, 정작 필요한 「곡선자 변경」 조각은 못 찾았다(10단계 두 판 0/6). PHP 판은 Haiku 가 여러 줄로 답하면 마지막 줄만 써서 검색어가 조각난 경우도 있었다.

배운 것
  1. 찾기가 답을 정한다. 같은 Claude 모델 · 같은 지시문인데 정답이 20 대 36으로 갈렸다. 다른 것은 검색뿐이다.
  2. 자르는 방법이 검색만큼 중요하다. 제목 한 줄이 빠지자 쉬운 1단계 질문을 틀렸다. 조각을 눈으로 몇 개 열어 보는 일을 건너뛰면 안 된다.
  3. 작은 규칙 하나가 한 언어를 통째로 망친다. 한글 판별 규칙 하나 때문에 PHP 판 일본어 적중이 2/10 이었다. 언어마다 따로 재야 보인다.
  4. 다국어 임베딩은 번역 없이도 꽤 찾는다. 도커 판 일본어 적중 9/10. 다만 크메르어처럼 약한 언어는 따로 손봐야 한다.
  5. 「모른다」는 잘 지켰다. 두 판 모두 자료 밖 질문 6/6. 지시문 한 줄과 근거만 주는 구조로 충분했다.
  6. 채점도 AI 에게 맡길 수 있지만 사람이 몇 건은 읽는다. 이번엔 8건 대조해 8건 모두 같은 판정이었다.
